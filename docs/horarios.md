# Registro de horarios (HU-HOR-01)

- Aplicar la migración `1792190000000-CreateSchedules` mediante el flujo existente de migraciones y ejecutar el seed de control de acceso. El permiso `schedule.create` se asigna al rol DOCTOR; sigue administrándose mediante permisos existentes.
- `POST /schedules`: cuerpo `{ "idSpecialty": 1, "date": "2026-11-02", "startTime": "09:00", "endTime": "12:00" }`. Requiere autenticación y `schedule.create`. El médico se obtiene exclusivamente de la sesión, incluso para SUPERADMIN. No se incorpora una excepción administrativa para registrar horarios ajenos.
- `GET /schedules/specialties?page=1&limit=10`: especialidades activas del médico autenticado, con paginación común de TASK-API-01 y proyección mínima.
- Formulario: `/dashboard/schedules/register`, accesible desde el menú según permiso.
- Modelo de bloques por fecha concreta, sin recurrencia. El día se deriva de la fecha y no se almacena duplicado. Fecha y horas representan tiempo civil de `America/La_Paz`, sin conversiones implícitas a UTC. No se permiten bloques nocturnos que crucen de día; registrar un bloque para cada fecha.
- Inicio estrictamente anterior al fin; intervalos adyacentes permitidos. Se rechazan solapamientos activos del mismo médico, incluso entre especialidades diferentes. Una transacción con bloqueo del médico serializa registros concurrentes y cambios de asignación de especialidades. No se eliminan horarios ni se almacena disponibilidad derivada.
- Requiere perfil, cuenta y rol médico activos, y especialidad activa asignada. No incluye consulta de horarios, modificación, disponibilidad ni citas de otras historias.

## Consulta de disponibilidad (HU-HOR-03)

- `GET /schedules/availability?idDoctor=3&date=2026-11-02&idSpecialty=2&page=1&limit=10` requiere sesión y `schedule.get-availability`. `idDoctor` y `date` son obligatorios; `idSpecialty` es opcional. La interfaz permite consultar una fecha concreta (sin rangos). Fecha ISO `AAAA-MM-DD` válida, identificadores enteros positivos y paginación común (máximo 100).
- El seed incorpora `schedule.get-availability` a PATIENT, STAFF y SUPERADMIN. La interfaz reutiliza el selector de HU-MED-04 y requiere también `doctor.get-by-specialty`; no necesita permisos administrativos. Ejecutar el seed con el procedimiento existente y renovar la sesión para recibir los permisos actualizados.
- Vista `/dashboard/schedules/availability`: selección paginada de especialidad/médico, fecha, consulta, carga, errores con reintento y resultado vacío. Cada listado usa TASK-API-01.
- Se derivan bloques de horarios activos, no eliminados, con inicio anterior al fin y comienzo futuro en `America/La_Paz`. Se exigen médico, cuenta, rol DOCTOR y especialidad activos y no eliminados. La especialidad debe seguir asignada al médico. Médicos inexistentes/inactivos, especialidades inactivas/no asignadas y fechas sin horarios elegibles producen una página vacía válida; fechas malformadas producen 400.
- Respuesta: `{ data: [{ idSchedule, idDoctor, idSpecialty, date, startTime, endTime, timeZone: "America/La_Paz" }], meta: { page, limit, total, totalPages }, ... }`, con el envoltorio HTTP existente. No se exponen datos de cuentas, auditoría ni estados internos.
- Los bloques representan intervalos de atención, no turnos de duración fija. EPIC-04 deberá descontar citas ocupadas antes de paginar y contar; podrá dividir un bloque conservando `idSchedule` y los límites del intervalo devuelto. No se almacena disponibilidad ni se implementan citas en esta HU. Una consulta no garantiza una reserva: EPIC-04 deberá revalidar y reservar de forma atómica.
- No requiere nuevas tablas ni migraciones. En esta rama no existe la implementación de HU-HOR-02; esta consulta trabaja sobre el estado vigente del modelo de HU-HOR-01 y no implementa modificación de horarios.
